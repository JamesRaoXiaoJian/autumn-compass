# Daily 2027 backend recruitment maintenance

Work only in the Git repository root used as the current working directory. This prompt is self-contained for unattended runs; do not look for operator-private instruction files.

Perform a freshness audit only of records explicitly set to `maintenanceStatus: '自动维护'`. This public example catalog tracks 2027 graduate full-time backend development roles only.

The company allowlist is fixed to **小米集团、字节跳动、美团**. Keep exactly two catalog slots per company and six records in total. Every slot must be a backend or server-side full-time graduate role; when fewer than two concrete eligible roles can be verified for a company, retain a truthful `待开放` placeholder with no job/application link instead of inventing a position. Never add, discover, substitute, or materialize a fourth company. Frontend, client, algorithm-research, data-science, product, hardware, and other non-backend roles are outside this public example catalog.

Read the server's redacted scope from `/api/recruitment-maintenance-scope` (on the default Linux stack: `curl --fail --silent --show-error http://127.0.0.1:${AUTUMN_COMPASS_PORT:-5173}/api/recruitment-maintenance-scope`). If the service is offline, use the redacted `recruitment-maintenance-scope.json` projection stored beside the configured SQLite database. Do not call `/api/workspace`, open the SQLite database, or read/copy workflow state, notes, interviews, resume data, or any other full-workspace value. The effective catalog is `(initialJobs - explicitly deleted job IDs/fingerprints) + server-side manually added jobs`; the audit scope is only effective-catalog records with `maintenanceStatus: '自动维护'`. Treat a missing or invalid value as `自动维护` for safety. Missing data is not a tombstone: if neither redacted source is available, audit only `自动维护` seed records non-destructively and do not infer, recreate, or remove any server-side addition/deletion.

`无需维护` is an explicit exclusion from this recurring task. Do not live-check, refresh, change `verifiedAt`, or automatically re-enable those records. Do not discover or add unrelated companies or positions during an unattended run. You may only clarify an existing `自动维护` backend record at the same allowlisted company while preserving its ID. Keep exactly two catalog slots per allowlisted company. Manually added records outside the allowlist remain server-side user data: do not audit, delete, or copy them into source.

Use a company-scoped `jobCode` as the stable identity for the same position when available; otherwise use its normalized ordinary job-detail URL, excluding referral and tracking variants. Preserve the existing record `id` for every match, including manually added records, so user edits and tombstones stay attached. Referral URLs/codes are private application metadata: the redacted scope excludes them, maintenance must not read or reconstruct them, and the catalog merge preserves their server-side values.

The board scope is 2027 graduate full-time backend recruitment only. Exclude internships, daily internships, research internships, social hiring, doctorate-only programs, and non-backend positions from open-company and actionable-job counts. Do not add their role links as tracked opportunities. If an allowlisted company exposes only excluded programs, keep the required `待开放` backend placeholder with no job/application link and document the exclusion; retain its official company or recruitment homepage separately as `companyUrl` when available. Keep formal 2027 new-graduate backend special programs even when they recruit year-round.

## Required workflow

1. Read the current seed data, the previous `maintenance/latest-run.md` report, and the redacted maintenance scope described above. Record whether the endpoint, the projection, or the non-destructive fallback supplied the scope.
2. Audit only 小米集团、字节跳动、美团 when represented by at least one `自动维护` seed record, in parallel where possible. Prefer official position detail pages, recruitment APIs, and official campaign announcements. Do not search for candidate companies outside the allowlist.
3. For every tracked record, check whether the exact role and application action remain available. Verify application start/end dates, campaign status, job ID, location, and URL semantics when the source exposes them.
4. Search official campus listings only as needed to clarify the two existing backend slots at each allowlisted company. Do not add companies or a third position for any company. A confirmed backend role may replace an unresolved placeholder at the same company under the same ID and must have an exact role-level link or a clearly labelled precision-filter link; excluded internship, social-hiring, doctorate-only, and non-backend results may be cited as evidence but must not become tracked application records.
5. Preserve the ordinary role-level job-detail URL. Do not read, copy, infer, or overwrite private referral parameters/codes, and do not replace a role-level link with a company portal.
6. Never infer dates or closure from silence, search snippets, or a single transient error. Leave unknown dates blank and document uncertainty. If evidence conflicts, prefer the official live source and record the conflict.
7. Make the smallest necessary edits to `apps/web/src/data/recruitment.ts` (re-exported by `apps/web/src/data.ts`) and related types/UI only when the data model genuinely requires it. The resulting public seed must still contain only the three allowlisted companies, exactly two slots each, and backend graduate full-time roles/placeholders only. When an `自动维护` record becomes concrete and evidence-bounded, set it to `无需维护`; otherwise leave it `自动维护`. Never automatically re-enable a `无需维护` record. Remove a seed record only when its ID/stable fingerprint is explicitly deleted, and retain its minimal ID/company/title/jobCode/ordinary-URL identity in `retiredJobIdentities` so legacy ID tombstones gain stable fingerprints. A relevant manually added backend record may be materialized only when it belongs to an allowlisted company and replaces one of that company's two existing slots under its existing ID; never create a duplicate, a third slot, or a new company, and never copy server workflow, priority, notes, interviews, or resume fields. Preserve all user-edit merge behavior in `useJobs`. Every accepted change to `initialJobs` or `retiredJobIdentities` must also increment the strictly monotonic exported `jobCatalogRevision`; never reuse or lower a revision, because the marker is the one-way fence that applies a catalog migration once without letting an older browser overwrite newer server recruitment data.
8. Do not read, initialize, clear, or mutate the live SQLite workspace or browser caches; do not copy workflow/notes into source files; do not submit applications, send messages, commit, push, or change GitHub/account settings.
9. Run `npm run typecheck` and `npm run build` after any source change. If no source changes are necessary, still run `npm run typecheck`.
10. Replace `maintenance/latest-run.md` with a concise report containing:
    - audit timestamp in Asia/Shanghai;
    - scope source plus which of the three allowlisted companies and six catalog slots were checked;
    - scope reconciliation, including explicit deletions honored and manually added positions incorporated;
    - exact data changes and official evidence links;
    - unchanged/open, unresolved, newly found, and closed/expired summaries;
    - a separate excluded-results note for internships, social hiring, doctorate-only, and non-backend programs, none of which may be included in autumn-recruitment counts;
    - validation commands and results;
    - a clear statement when nothing material changed.
11. Leave all validated maintenance edits in the working tree for explicit user review. Do not create a Git commit and never push. If validation fails, leave the evidence report clear about the failure and describe it in the final response.

Keep the final response concise and state the scope source, whether files changed, whether validation passed, that changes remain uncommitted, and which items require user review.
